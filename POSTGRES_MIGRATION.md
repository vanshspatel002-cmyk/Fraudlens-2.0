## SQL and transaction choices

- `src/postgres.py` bridges the existing parameterized DB-API calls. It only
  translates `?` markers outside literals/comments to driver parameters. It
  does not interpolate user values or attempt general SQLite SQL rewriting.
  Rows support both numeric and named access, matching the existing contracts.
- Explicit file paths always choose SQLite, even with `DATABASE_URL` present.
  `FRAUDLENS_DB=postgresql` chooses the private backend URL; with no explicit
  file override, a configured URL selects PostgreSQL. URL credentials never
  become a filename, log label or frontend value.
- Version `001_initial.sql` is explicit, checksum-verified and transactional.
  HTTP requests verify the installed version; they do not create/migrate tables.
  Existing target schemas are never silently amended or reset. Future schema
  changes require a new migration/version and a reviewed upgrade path.
- Text IDs/hashes are retained. Explicit `rowid BIGINT GENERATED BY DEFAULT AS
  IDENTITY` columns preserve causal ordering independently of wall-clock time.
  Import preserves those IDs and advances each sequence past its maximum.
- SQLite REAL becomes DOUBLE PRECISION, not PostgreSQL's single-precision
  REAL. Integers become BIGINT. ISO timestamps/date strings and JSON retain
  their original TEXT representation, including timezone offsets and bytes.
  Epoch times remain double precision. New migration metadata uses TIMESTAMPTZ.
  JSON casts/type constraints validate structured data; JSON operators/array
  expansion and metadata introspection use explicit dialect implementations.
- Embeddings remain stored JSON and numpy search. No pgvector conversion,
  changed similarity policy or rebuilt perception is implied.
- Upserts use explicit column lists and `ON CONFLICT`; report insertion is
  idempotent and an update/delete trigger protects report history. Foreign
  keys cover cases/evidence/runs/decisions and cross-case run associations.
  Run finding/image JSON relationships are additionally validated on import.
  Cases intentionally retain the preexisting non-FK claimant identifier:
  intake can create a case before a separate claimant row (12 such demo cases).
  Global/historical audit case references retain their original semantics.
- Submission acceptance, receipt, idempotency response, evidence batch, audit
  and enqueue share a write transaction. PostgreSQL advisory key locks protect
  simultaneous first-use submission keys. Case row locks serialize evidence,
  decisions and reprocessing; the partial unique index enforces one active job.
- Claims use `FOR UPDATE SKIP LOCKED`. One cluster leader holds a transaction
  advisory lock on a dedicated connection. This works with transaction poolers
  by pinning that transaction; it consumes one database connection while idle.
  Standbys can take leadership after connection/process loss. Recovery remains
  bounded to three attempts and reconciles already committed run results.
  Every attempt receives a token checked under row lock before progress/result
  persistence; a recovered old worker cannot commit findings or overwrite state.
  A five-second heartbeat keeps the guard alive during long model work; its
  120-second default idle timeout bounds orphan leadership while tolerating cold
  Windows model imports. `FRAUDLENS_PG_LEADER_TIMEOUT_SECONDS` accepts 10–300;
  the regression uses a shortened limit. Recovery uses a monotonic
  database transaction epoch and skips newer work. Loss releases only the
  worker's own matching attempt, never a subsequently claimed attempt.
  SQLite retains its existing Windows/POSIX worker lock.
- Ordinary reads are short transactions. API GETs use a coherent repeatable-read
  read-only snapshot. Transaction-local schema/timeouts avoid pooler state
  leakage; prepared statements are disabled for pooler compatibility. A bounded
  psycopg pool returns/rolls back connections in `finally` and closes at process
  exit. Borrow-time health checks discard stale connections. Regular idle
  transactions expire after 90 seconds. Remote connections require TLS. Driver
  error details are sanitized; rollback failure does not mask the original error.
  Psycopg pipelining batches transaction setup/reads/commit into one network wait;
  it retains explicit write transaction boundaries and rolls failed reads back.
- Lost COMMIT acknowledgement is ambiguous. Upload handlers retain files and
  return an explicit unconfirmed-save response. An identical submission key
  safely replays committed acceptance, or creates one acceptance if the first
  transaction rolled back. Supplementary applicants refresh tracking before
  retrying. `audit_evidence_paths.py` reports missing/hash-mismatched/unreferenced
  files read-only; it never deletes evidence on an assumption about COMMIT.
- Queue summaries use batched reads to avoid hundreds of network round trips.
  Frontend automatic queue/detail refreshes wait for the preceding response,
  preventing slow cloud requests from permanently invalidating one another.
  Provider calls and slow admission remain outside submission write locks.
  `/health` does not run the full research integrity verifier over PostgreSQL;
  its explicit status says `offline_research_verifier_required`. Historical
  ablation outputs remain preserved; health does not certify their accuracy.

## Private schema and permissions

Application objects live outside `public`. Installation revokes schema, table,
sequence and function privileges from PUBLIC, `anon`, `authenticated` and
`service_role`, including defaults for objects created by this owner. RLS is
enabled on all 22 tables with no browser policies. Backend connections use the
configured server-side database owner; owner/BYPASSRLS access is intentional.
No project-wide exposed-schema setting or unrelated public grant is changed.
Do not add this schema to browser/Data API exposure. SQL grants and RLS still
deny browser roles if it is accidentally exposed. The isolated suite tests
both roles against every application/metadata table.

This is one organization, not tenant isolation. The current backend URL is
privileged; a separately provisioned least-privilege service login, controlled
credential rotation, security review and deployment-specific API settings are
production requirements. No service password or browser database key was added.
Database coordination is independent of host-local locks; shared evidence
storage, a distributed provider budget and a complete multi-host deployment
are not implemented or claimed by this local migration.
See [Supabase security guidance](https://supabase.com/docs/guides/database/secure-data),
[RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) and
[psycopg pooling](https://www.psycopg.org/psycopg3/docs/advanced/pool.html).
